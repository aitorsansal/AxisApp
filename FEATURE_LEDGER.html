New features

None of these exist today in any form. Ordered by build cost, cheapest first.

Quick IOU
cheapno schema change

A one-participant Expense with a single ExpenseShare and is_settlement = false is already, in full, "I lent Marc €20" — the schema already supports it. What's missing is a UI shortcut: a single quick-entry sheet (payer defaults to you, one participant, no category/receipt/split screens) that writes the exact same row AddExpensePage would, just without walking through N-way split UI for what's really a two-person loan.

Ledger export
cheap–mediumpure read

A CSV/PDF settlement statement, for taxes, a dispute, or leaving a group with a receipt of shared history. Generated client-side or via a small Edge Function straight from expenses/expense_shares, scoped by the RLS a member already has — no new table, no new policy, no new access rule to reason about.

Category budgets per group
medium+1 table

A monthly cap per category ("Groceries: €400/mo"), a progress bar on GroupDetailPage, one nudge when a category crosses it. A new category_budgets table (group_id, category, monthly_limit) read against expenses already converted to the group's currency — the RLS is the same group-scoped shape every other table here already uses, nothing novel to invent.

One-screen overview
mediumno schema change

Front the flat Groups list with a single dashboard: net balance across every group you're in, and the next three upcoming events across all of them. Every number already lives in my_group_balances and events/event_attendees — this is a new screen and a couple of aggregating queries across groups, not new data.

Where are we eating
medium–large+3 tables

A lightweight Doodle-style poll inside a group: propose 2–6 options (restaurant, date, time), members vote, and a winning "when" option can pre-fill AddEventPage. New polls/poll_options/poll_votes tables, with group-scoped RLS that mirrors events/event_attendees almost clause for clause.

When's everyone actually free
mediumreuses poll tablesproduct pass

A step before "Where are we eating" even applies: a lightweight weekly availability grid a group fills in together (free / busy / maybe per day), so picking a date for the poll above stops happening in a separate group chat. Same polls-shaped schema as the item above with a grid-shaped option set instead of a short list — the two features share infrastructure and are worth building in the same pass, not sequentially.

Favors, not just money
medium+1 tableproduct pass

Real household friction isn't only cash — "you drove last time," "I did the bins this week," "you owe me a ride to the airport" are debts too, and today they live nowhere. A parallel, lightweight favor_ledger table (group_id, from_member_id, to_member_id, description, settled_at) reusing the member model exactly as-is, surfaced as its own small list next to balances rather than forced into expenses, which is genuinely about money.

Trip mode
large+1 nullable columnproduct pass

A weekend away spins up a burst of expenses and one or two events that don't deserve a permanent group cluttering the Groups list forever, but also don't belong crammed into an existing household group. A groups.archived_at (or a lightweight occasion_starts_at/ occasion_ends_at pair) lets a group be created, used hard for a week, then auto-collapse to a single summarized card instead of sitting in the list at equal weight to "Family" forever. The riskiest part isn't schema — it's deciding what "collapsed" looks like in the UI without hiding a balance someone still owes.

Subscribe, don't sync
medium–largenew Edge Function + signed token

A per-group, per-member signed ICS URL that Apple/Google/Outlook Calendar can subscribe to read-only — events and birthdays, no OAuth. A real, cheap precursor to the deferred Phase 2.5 Google sync that ships value now without touching that later two-way work. Needs a new Edge Function endpoint and a signed per-member token; the one real risk is making sure that token can't be replayed to see anything beyond what that member's own RLS already permits.

Recurring events, not just recurring expenses
large+1 column, +1 cron job

events has no recurrence today — only recurring_expenses and the birthday auto-generator materialize on a schedule. A weekly game night currently means re-creating the event by hand, every week, forever. Add a simple recurrence_rule (interval + unit + optional end — not full RRULE) and a materialize_recurring_events() job on the same pg_cron pattern as materialize_recurring_expenses(). This would be the third instance of the identical shape in this codebase — worth factoring the pattern out once rather than hand-rolling it a third time. Natural follow-on once this exists: let a recurring event's RSVP close-out offer to pre-fill an expense from last time's split ("same as usual?"), instead of the group re-deciding the split fresh every week.

Switch without losing history
largenew parsing + review UI

The single biggest adoption blocker for anyone currently on Splitwise or Tricount is re-entering months of history by hand. A CSV importer that parses each app's export shape into a review screen — draft expenses, editable before commit, never written straight to the ledger — removes that. The most engineering-heavy item on this list: two different export shapes to support, and real care needed so a bad column-guess doesn't silently attribute an expense to the wrong phantom member.

Upgrades to what's already shipped

Each of these starts from a real, current behavior — verified against the live schema and view-model code, not assumed from the docs.

Invite links: expose what the schema already does
cheapUI only

invites.expires_at / invites.max_uses already exist and already default to a 7-day, single-use link — but nothing in the invite UI lets someone dial that down to "24 hours, one use" for an in-person hand-off, and there's no QR code, so the token still has to be read out loud or copy-pasted. Expose both fields as options at invite-creation time and render the code as a QR. No schema change — the columns are already there.

Percentage & shares/weight split modes
cheap–mediumUI only

AddExpenseViewModel already has a manual escape hatch (IsManualSplit) where every participant's amount is directly editable on top of the default equal split, and expense_shares.share_amount already stores whatever number it's given. This is not "add splitting" — it's adding two more entry modes (60/40 percentages, or "2 shares for me, 1 for the kid") that compute share_amount for you, on a column that's always been able to hold it.

Expense search & filter
mediummaybe +1 index

By member, category, date range, and free text on the description, scoped to one group. Every row is already RLS-visible to a member of that group — this is a filtered read, plus possibly one index on expenses(group_id, occurred_at), not a new access rule.

Per-member display currency
mediumlocal preference

View every amount converted to your own currency without touching the group's canonical groups.currency or its stored amount_in_group_currency. exchange_rates is already cached daily — this is client-side math at render time plus a Preferences key, the same non-synced, per-device shape BalanceDisplayModePrefix already established for the simplified/pairwise toggle.

Configurable event reminder lead-time
mediumcron scan-window change

Today's schedule is fixed — daily plus day-of, by deliberate Phase 2 design. Letting someone pick "1 hour before" vs. "1 day before," per event or as a Profile default, means widening the reminder job's due-scan window and reading one new column — the same shape of change as materialize_recurring_expenses()'s existing due-scan, not a new subsystem.

RSVP deadline, one nudge
medium+1 column, reuses reminder jobproduct pass

Distinct from the lead-time upgrade above: an organizer sets "please respond by Friday," and anyone still un-RSVP'd at that point gets exactly one targeted nudge — not a repeat of the standard event reminder, and not left to whoever notices the pending invite in a list. Same event_attendees due-scan shape, filtered to response is null.

Multiple receipt photos per expense
mediumschema change

Expense.receipt_path is a single column today — a restaurant bill split three ways sometimes has three photos (the bill, a card slip, a tip line). Move to a child expense_receipts table (expense_id, storage_path), reusing the exact resize/upload/signed-URL/cleanup infrastructure the receipts bucket already has. Real schema work, but zero new subsystems.

Balance aging, not just amount
mediumview changeproduct pass

A €5 debt from eight months ago and a €5 debt from yesterday read identically today — same number, same view. Surfacing "owed since" alongside the amount (oldest contributing expense row per pairwise balance, not a new table) lets someone actually see what's gone stale versus what's just normal week-to-week ebb and flow, which the existing simplified/ pairwise views don't distinguish at all.

A line after settling up
medium+1 columnproduct pass

Right now a full settle-up is just another row mixed into the same activity feed as everything before and after it — there's no equivalent of a bank statement's period boundary. A groups.last_settled_at, stamped whenever every pairwise balance in a group hits zero, lets the activity feed group itself into "since last settle-up" versus history, without changing how balances are computed at all.

Group activity trail
medium–large+1 table, +N triggers

Multiple people can add, edit, or delete an expense or event in the same group today with zero record of who touched what last — thin for two people, thinner for a family group where "did Dad delete that, or did it just not sync?" is a real question that comes up. A new activity_log table plus AFTER INSERT/UPDATE/DELETE triggers on expenses/events (the same trigger-driven shape expense_shares_snapshot_currency_conversion already uses), RLS mirroring "visible if you can see the parent group."

Shared group admins, not just one owner
largeRLS audit, not a column migration

Every group has exactly one created_by owner today, plus transfer_group_ownership() to hand the whole thing to someone else — no co-admin concept exists (group_members has no role column at all). A role (owner/admin/member) sounds like one column, but it touches every policy currently written against created_by = auth.uid() on groups/ group_members, plus leave_group()'s "creator can't leave" guard and transfer_group_ownership()'s own logic. This is the one item here that's a genuine RLS-policy audit, not a quick add-on — worth doing deliberately, on its own, not folded into something else.

☰

Council cross-check — schema pass

A pass run independently against supabase/schema.sql and the ViewModel code rather than the docs, to catch anything above that's wrong or already half-built.

  • Correction folded in: the split-mode upgrade originally read "add splitting" — it doesn't need to. AddExpenseViewModel.IsManualSplit already lets every participant's amount be edited by hand; the real gap is percentage/shares math on top of an already-flexible share_amount column.
  • Correction folded in: the invite-link upgrade originally proposed adding expiry and use-limits. Both columns (expires_at, max_uses) already exist in schema.sql and are enforced in redeem_invite() — the actual gap is only in the client UI and the missing QR code.
  • Confirmed, not already present: events has no recurrence column and group_members has no role column — both new-feature/upgrade framings above hold as written.
  • Strongest picks, technically: Quick IOU and the split-mode upgrade — both ship real value on data the schema already carries, with no migration risk.
◆

Council cross-check — product pass

A second, independent pass run purely from the household/friend-group use case — no schema in hand — to catch what a code-first read tends to miss. Marked product pass above; folded in only where it didn't overlap something the schema pass already covered (its "expense edit history" idea, for instance, is the same gap the activity trail above already fills, so it isn't listed twice).

  • Its own strongest pick: favors-not-money and balance aging — both point at the same real gap, that Axis currently treats every debt as financially and temporally identical, which isn't how households actually experience owing each other things.
  • Cut by that pass itself, before it reached me: a shared shopping list (too close to the already-dropped shared-lists vertical) and splitting by percentage-of-income (interesting, too niche for a friend group).

Considered and cut

In the same spirit as POSSIBLE_FEATURES.md's own "explicitly dropped" list — kept here so nobody re-proposes these without the reasoning attached.

×
Offline-first / local cache with background sync. Cuts against the product's own thesis — a real backend from day one — and turns "two phones edit the same expense while offline" into a real conflict-resolution surface, for a problem shared-wifi group chats mostly don't have.
×
Biometric / PIN app lock, as a feature slot. The concern is real — this is shared financial data — but it's a security-hardening task, not a roadmap feature; it belongs in a dedicated security pass, not competing for priority against the ideas above.
×
Event photo gallery. Would reuse the receipts bucket's exact upload/resize infrastructure for a much rarer case (party photos vs. a tax receipt) — speculative until someone actually asks for it.
×
Full RRULE recurrence on events. Matching Google's actual RRULE grammar is Phase 2.5's problem the moment real two-way Google sync gets built — a simpler interval-based rule now avoids solving the hard version of this twice.
×
Splitting by percentage-of-income. A genuinely used pattern in some households, but a fairness model, not a splitting mechanic — it needs each member to disclose income to the group, which is a much bigger ask than anything else on this page and not a fit for a friends-and-family default.
