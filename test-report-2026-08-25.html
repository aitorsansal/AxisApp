The goal was to walk the app start to finish as a real user would: sign up, build out two groups of people (mostly phantom members who never sign in), and record expenses in a few different shapes — equal splits, uneven manual splits, and an expense paid by someone other than the account running the app. Every step ran against the live Supabase project through the actual Windows build, not mocked. Seven real, previously-unverified bugs turned up along the way — five were launch/data-integrity blockers, and a sixth (found by the user, not automation) was a balance-sign inversion that would have shown every user the exact opposite of who owed whom. All six got fixed and re-verified live; the seventh is a systemic reliability gap that's flagged but not fixed (see below).

What actually got tested

  • Sign-up (SupabaseAuthService) → session persists → lands on Groups
  • Create a group (Roommates, then Family)
  • Add 5+ phantom members to a group (10 total across both groups: 5 in Roommates, 3 in Family, plus the 2 real-account memberships)
  • Two groups, each with ≥4 members (Family: 4, Roommates: 6)
  • Equal-split expense across all 6 group members, real account as payer — verified 120.00 / 6 = 20.00 each in the DB
  • Manual/unequal-split expense, paid by a phantom member (Carlos Ruiz) — shares of 5/5/30/20/15/15 summing to 90.00, verified in the DB
  • Expense where the real account is neither payer nor a split participant — not isolated as its own case (checkbox automation in the split list wasn't reliably clickable in the time available); the manual-split expense above does prove a non-user payer works end-to-end, and the real account's minimal 15.00 share there is close to but not the same as full exclusion
  • Claiming a phantom via invite redemption, recurring payments, receipts — out of scope for this pass; invite generation is covered (see AX-05) but redemption itself wasn't exercised

Bugs found this session

In discovery order. AX-01 through AX-05 all shared the same shape: a Postgrest insert whose payload silently didn't match what the RLS policy or the schema expected, and every one of them surfaced as a full application crash rather than an error message — see AX-07. AX-06 is a different kind of bug entirely — no crash, just wrong output — and is the reason a human read-through of the actual numbers on screen still matters even after everything else is green.

AX-01 — Shell.Current.DisplayPromptAsync crashes the app on Windows

blocker GroupsViewModel.NewGroup

The original "+ New group" flow used a native prompt dialog. On this WinUI build it fails fast with 0xc000027b the instant it's invoked — a known WinUI ContentDialog issue (microsoft-ui-xaml#10897), not something fixable by changing how the call is made.

Fix: replaced the native prompt with a real page, NewGroupPage/NewGroupViewModel, wired through Shell routing like every other page in the app. Confirmed group creation no longer crashes.

AX-02 — Creating a group failed with an RLS violation on group_members

blocker supabase/schema.sql — select group_members in your groups policy

Same root cause as a bug already documented for the groups table (see CLAUDE.md): the creator's own group_members insert does INSERT ... RETURNING, which has to satisfy the table's SELECT policy — and is_group_member(group_id) is still false at that exact instant, since this insert is what would make it true.

Fix: widened the policy to is_group_member(group_id) or exists (select 1 from groups g where g.id = group_id and g.created_by = auth.uid()), mirroring the existing groups fix. Applied to schema.sql and the live DB.

AX-03 — GroupMember/ExpenseShare composite keys silently dropped from every insert

blocker, broad Models/GroupMember.cs, Models/ExpenseShare.cs

Both models mark their first key column [PrimaryKey("...", false)] — the false means don't insert this column, which is right for an auto-generated key but wrong here: group_id and expense_id are required foreign keys with no default. Every insert silently omitted them, which failed NOT NULL/RLS and read back as the same generic "new row violates row-level security policy" message AX-02 also produces — this one would have blocked every group-membership insert and every expense-split insert in the app, not just group creation.

Fix: changed both to shouldInsert: true. Confirmed via a real group_members row with a correct, non-null group_id.

AX-04 — Adding a phantom member crashed with an RLS violation on members

blocker supabase/schema.sql — select members you can see policy

Exactly the pattern CLAUDE.md already flagged as "plausible, not yet confirmed" for AddPhantomAsync: a freshly-inserted phantom (account_id null, no group_members row yet) satisfies neither account_id = auth.uid() nor the group-membership subquery in the SELECT policy, at the exact instant the INSERT tries to return the new row.

Fix: added or created_by = auth.uid() to the policy — the same pattern used for groups and (now) group_members. Applied to schema.sql and the live DB; phantom creation confirmed working afterward.

AX-05 — Every invite after the first collided on an empty token

blocker Models/Invite.cs, Services/SupabaseInvitesRepository.cs

Invite.Token is a plain [Column] string defaulting to "" in C#. Postgrest sends that literal empty string on every insert, overriding the table's default encode(gen_random_bytes(9), 'base64url'). The very first invite ever created for the account succeeded with token = ''; every invite after that hit invites_token_key's unique constraint and crashed — meaning phantom-member invites (which create one per phantom) worked at most once per account, ever.

Fix: SupabaseInvitesRepository.CreateAsync now generates the token client-side with RandomNumberGenerator instead of trusting the column default. Confirmed a real invite code (e.g. bmc9OyhsBFbw) after the fix, and added 4 more phantom members with no further collisions.

AX-06 — Member balance captions showed the exact opposite of who owed whom

high — wrong money direction ViewModels/GroupDetailViewModel.cs — ApplyBalance

Found by the user while reviewing the app, not by automated testing — after the $120 equal-split expense (paid by the real account), every other member showed "you owe" even though they were the ones who owed money back; after the $90 expense paid by phantom Carlos Ruiz, Carlos himself showed "owes you" even though the real account owed him. The two branches in GroupDetailViewModel.ApplyBalance had the sign backwards relative to group_balances' documented convention (positive = the group/you owe them) — they'd been copy-pasted from GroupsViewModel.ApplyBalance, which reads a different view (my_group_balances, the current account's own balance) where that same sign check is correct. For any other member's balance the relationship inverts: their positive balance means you owe them, not the other way round.

Fix: swapped which branch sets IsOwed/IsOwing and the "owes you"/"you owe" captions. Rebuilt and confirmed against the live data: Carlos Ruiz (net creditor, +$65) now correctly shows "you owe" $65.00 in red, and Maria/David/Elena/Ana (net debtors) show "owes you" in green with the right amounts ($25/$50/$40/$35) — all matching a hand-computed balance sheet from the two seeded expenses.

AX-07 — Any unhandled exception from an async command crashes the whole app

not fixed — systemic affects every [RelayCommand] async method

This is the pattern behind every crash above, plus two more encountered that aren't code bugs in themselves: a transient Supabase "JWT issued at future" clock-skew rejection during a pull-to-refresh, and a CopyLink command failing with COMException 0x80070490 because this unpackaged Win32 build isn't registered for the modern Toast/AppNotificationManager API. Neither of those is worth fixing on its own — but in every one of these cases, CommunityToolkit.Mvvm's AsyncRelayCommand posts the exception back to the WinUI dispatcher, which responds by fail-fasting the entire process (0xc000027b) instead of the command just... failing. A real user hitting any transient network hiccup, RLS edge case, or platform API gap loses the whole app, with no error shown and no chance to retry.

Recommendation: add a global handler — either wrap relay-command bodies in a try/catch that surfaces a toast/snackbar-style error (skipping the broken CommunityToolkit.Maui.Alerts.Toast on Windows), or hook AsyncRelayCommand's built-in exception handling (IAsyncRelayCommand.ExecutionTask / a shared FlowExceptionsToTaskScheduler-style base) so failures degrade to an inline error state instead of fail-fast. Not attempted here — flagged for a follow-up pass since it touches every ViewModel.

Design gap noted, not fixed

Raised mid-session and written into CLAUDE.md for whoever picks this up next: phantom members are currently scoped per-group. Adding "Maria Lopez" in two different groups creates two unrelated members rows, not one shared identity — and since claiming links an account to exactly one members row (invites.target_member_id), a real Maria signing up would only ever reconnect to one of her two phantom histories. No fix decided; see CLAUDE.md's "Known gap, not yet designed" note under the members/accounts design section for the open questions (dedupe by name? explicit link step? a person-concept above members?).

Method notes

Driven end-to-end through the real Windows build (windows-mcp for UI automation) against the live Supabase project, with direct SQL verification after each step via the Supabase SQL editor (claude-in-chrome). Every crash was diagnosed from %TEMP%\axisapp-crash.log (an existing AppDomain.UnhandledException hook in Platforms/Windows/App.xaml.cs) rather than guessed at, which is what made AX-02 through AX-05 traceable to an exact line instead of just "the app closed."
