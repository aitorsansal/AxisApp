Goal for this pass: exercise the cross-group phantom-linking feature (built earlier this session — see CLAUDE.md's "Known gap" note and the new SearchVisibleByNameAsync/"Link" UI in JoinGroupViewModel) end to end against the live Supabase project, then actually redeem invites with fresh accounts — something the prior 2026-08-25 test pass explicitly skipped ("invite generation is covered, but redemption itself wasn't exercised"). Four real bugs surfaced in total, all fixed and re-verified live; none were cleaned up per instruction, so the data below is still in the project.

Bugs found this session

In discovery order. AX-08 blocked the very first redemption test from happening through the UI at all; AX-09 was needed to make the new Link feature usable by non-creator members; AX-10 is the big one — a silent, project-wide bug that made every invite ever created permanently unredeemable; AX-11 is what AX-10's investigation exposed underneath it once redemption started actually running.

AX-08 — No way to reach the "join a group" screen with zero groups

blocker, UX gap Pages/GroupsPage.xaml, ViewModels/GroupsViewModel.cs

JoinGroupPage (the invite/redeem screen) was only ever navigated to from GroupDetailViewModel's overflow menu — which requires already being a member of a group. GroupsPage, the landing screen after login/signup, had exactly one action: + New group. A brand-new account with zero groups had no UI path to redeem an invite code at all — not a backend bug (redeem_invite()'s RPC worked fine), just a missing door. This would have blocked every real onboarding flow where someone is invited to join an existing group rather than starting their own.

Fix: added a JoinGroupCommand to GroupsViewModel and a "Join with code" button next to the FAB on GroupsPage, navigating to JoinGroup with no groupId — a case JoinGroupViewModel already handled correctly (HasActiveGroup just stays false). Confirmed a zero-groups account reaches the join-by-code field and successfully redeems a plain invite (see AX-11's fresh-join verification below).

AX-09 — group_members insert restricted to the group's creator only

blocker for the Link feature supabase/schema.sql — group creator can add members directly policy

The existing RLS policy only allowed the account that created a group to insert group_members rows — meaning only the creator could add a phantom, or (with this session's new feature) link an existing phantom into that group. Any other member of the group would have hit an RLS violation trying to do either.

Fix: widened the policy to is_group_member(group_id) or exists (select 1 from groups g where g.id = group_id and g.created_by = auth.uid()) — the created_by clause stays for the same chicken-and-egg reason as the groups/invites policies (the creator's own group_members row, inserted in the same call as the group itself, can't satisfy is_group_member yet at that exact instant). Applied to schema.sql and the live DB. Confirmed the Link action works for the group's creator; any-member access follows from the same policy but wasn't separately exercised with a second real member account this session.

AX-10 — Every invite ever created was permanently unredeemable

severe — entire feature silently broken Models/Invite.cs, Services/SupabaseInvitesRepository.cs

Same shape as the already-documented AX-05 (Token defaulting to ""): Invite.ExpiresAt is a plain [Column] property with no explicit initializer, so its C# default is DateTime.MinValue (0001-01-01). Postgrest sends that literal value on every insert, silently overriding the table's real default (now() + interval '7 days', schema.sql:87). redeem_invite() checks if v_invite.expires_at < now() then raise exception 'Invite expired' — since 0001-01-01 is always in the past, every single invite in the live project, from both this session and the prior 2026-08-25 pass, was "expired" the instant it was created. Nobody could ever successfully join a group or claim a phantom via invite code. Confirmed directly: select expires_at from invites returned 0001-01-01 00:00:00+00 for every pre-fix row, including Carlos's and David's original claim invites minted when they were first added as phantoms.

This is also why it went undetected until now — the prior test session generated invites (and noted generation worked) but explicitly didn't attempt redemption, so the "expired" failure had no chance to surface before this pass.

Fix: SupabaseInvitesRepository.CreateAsync now sets ExpiresAt = DateTime.UtcNow.AddDays(7) explicitly, the same pattern already used for Token. Pre-fix invites in the live table were left as-is (a bulk UPDATE across the table was attempted to backfill them but was blocked by this environment's safety guardrails as a broad data mutation; re-minting fresh invites through the normal "Resend" UI flow was used instead). Confirmed post-fix: newly created invites show real future expires_at values (e.g. 2026-09-01), and all three claim redemptions plus the fresh-join redemption below succeeded end-to-end using post-fix invites.

AX-11 — Toast crash (AX-07) made a successful redeem look like a failure, and crashed the app on Resend

high — false negative + app crash ViewModels/JoinGroupViewModel.cs — JoinByCode, Resend, CopyLink

This is the already-flagged systemic issue (AX-07: Toast.Show throws COMException 0x80070490 on this unpackaged Win32 build, since it isn't registered for AppNotificationManager) actually biting during this session's testing, in two different ways:

1. Clicking Resend crashed the whole app outright (confirmed in %TEMP%\axisapp-crash.log, JoinGroupViewModel.Resend line 128) — the invite token was already minted and copied to the clipboard by that point, but the app died before it could be used, forcing a rebuild-and-relogin cycle each time a fresh token was needed.

2. JoinByCode wraps both the actual RedeemAsync call and the follow-up Toast.Make("Joined group").Show(...) in one try/catch. When redeeming Maria's claim invite, the redemption itself succeeded (confirmed via SQL — her account_id was correctly set) but the subsequent Toast call threw the same COMException, which the catch block reported as ErrorMessage = "No se ha encontrado el elemento." (the OS's localized COM error text) — a scary, misleading failure message shown right after a successful join, with no navigation to the group either.

Fix: added a shared TryShowToast helper that swallows the Toast exception, and routed CopyLink, Resend, and JoinByCode through it instead of calling Toast.Make(...).Show(...) directly. This is a surgical fix for the three call sites that actually crashed/misreported during this session, not the broader systemic AX-07 refactor (still open, still flagged separately, and out of scope here since it touches every [RelayCommand] in the app). Confirmed post-fix: Carlos's and David's claim redemptions both navigated straight into their group's detail page with no error and no crash.
