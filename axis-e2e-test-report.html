The requested test plan — 5 phantom users, 2 groups of 4+, and a full matrix of payment/split scenarios — could not run. Every path in the plan requires creating a group first, and group creation itself is blocked by a Postgres/PostgREST anomaly that survives a full schema rebuild, a fresh JWT, and direct curl reproduction outside the app entirely. This report documents what was fixed along the way, exactly how the blocker was isolated, and what's left to try.

02 Bugs found and fixed

Four real, verified defects — independent of the blocker below. All are committed.

FixedNo client-side validation on sign-up
AxisApp/ViewModels/LoginViewModel.cs · AxisApp/Services/SupabaseAuthService.cs

Submitting the sign-up form with empty email/password fields wasn't rejected client-side — it reached Supabase, which interpreted the empty credentials as an anonymous sign-in attempt. Since anonymous sign-ins are disabled on this project, the user saw a raw JSON error (anonymous_provider_disabled) instead of a validation message.

FixedNo UI path to create a phantom member
AxisApp/ViewModels/JoinGroupViewModel.cs · AxisApp/Pages/JoinGroupPage.xaml · AxisApp/Services/SupabaseMembersRepository.cs

IMembersRepository.AddPhantomAsync existed in the data layer but nothing in the UI called it, and it never joined the new member to a group either. Added a name field + Add button on the Invite screen, an AddToGroupAsync repository method, and wired the two together with an invite so the phantom shows up as claimable.

FixedSupabase package was six major versions behind
AxisApp/AxisApp.csproj

The project was pinned to the deprecated supabase-csharp 0.16.2. Upgraded to the current Supabase 1.6.0 package (confirmed against a working reference project), which moved every model's Postgrest imports from Postgrest.* to Supabase.Postgrest.* — updated across all 19 affected files.

FixedSession not re-propagated to Postgrest after sign-in
AxisApp/Services/SupabaseAuthService.cs

client.InitializeAsync() was only called once at cold boot, before any user had signed in. Re-running it immediately after a successful sign-up/sign-in (matching the pattern in a known-working reference project) ensures the client's internal state picks up the freshly-established session.

03 The blocker

Unresolved

Inserting into groups or members always fails RLS — even with a verified-correct auth context

Every attempt to create a group returns:

{"code":"42501","message":"new row violates row-level security policy for table \"groups\""}

The policy is exactly with check (created_by = auth.uid()), and every value involved was independently confirmed correct — see the investigation trail below. The same account, same token, same instant, succeeds against categories (identical policy shape) and fails against groups and members.

Investigation trail

System clock skew ("JWT issued at future")
Real issue, fixed by resyncing the clock — but a separate, intermittent problem from the 42501 below
Supabase package not forwarding the session to Postgrest
Real issue, fixed (§2) — resolved the "No API key" / apikey-missing symptom, not this one
RLS policy text itself wrong
Ruled out — pg_policies shows with_check: (created_by = auth.uid()), byte-identical to categories, which works
Missing GRANT on the table or column
Ruled out — authenticated has full INSERT/SELECT/UPDATE/DELETE on both tables, identical to categories
JWT invalid or wrongly signed
Ruled out — decoded token has correct sub/role, and its signing key ID matches the project's live JWKS exactly
auth.uid() resolving incorrectly
Ruled out — a dedicated RPC (select auth.uid()) called through real PostgREST returns the exact right account ID
Stale schema / leftover state from earlier test runs
Ruled out — dropped and rebuilt the entire schema from schema.sql from scratch; identical failure on the first attempt against the fresh schema
C# client sending a bad request
Ruled out — replayed the identical insert via raw curl, completely outside the app; same 42501
categories (same policy shape) succeeds; groups/members fail
Confirmed anomaly — same token, same moment, different tables, different outcome

04 Recommended next steps

1 Open a Supabase support ticket

This looks like a platform-level issue with the project's Postgres/PostgREST instance, not anything fixable from application code, SQL policies, or grants — all of which were independently verified correct. The categories vs. groups/members split with an identical policy is the strongest evidence to lead with.

2 Try a project restart

Not attempted — restarting the underlying compute would clear any stuck connection-pool or prepared-statement state without needing a schema change. Available under Project Settings → Infrastructure.

3 As a last resort, spin up a fresh Supabase project

schema.sql is idempotent-safe to run once against a clean project and reproduces the full schema exactly. If a fresh project doesn't reproduce the bug, that confirms it's specific to this project's infrastructure state rather than the schema design.

4 Re-run this test plan once group creation works

Nothing else in the plan was reachable, so the phantom-member, multi-group, and split-payment scenarios are still entirely unverified — not known-broken, just untested.
