Part 1

Independent review

Read directly from the repository on branch claude/project-review-features-kgdc3f at commit 6c3c0c0 — no prior review content reused. Per instructions, the only Markdown file read was CLAUDE.md; the only SQL file read was supabase/schema.sql, not the one-off migration scripts beside it. EVENTS_PLAN.md, MULTI_CURRENCY_PLAN.md, REDESIGN_PLAN.md, README.md, and SCOPE.md exist and are sizeable (15–47 KB each) but were not read — every claim below is grounded in the code and schema themselves.

01What Axis actually is, right now

Axis is a .NET MAUI (net10.0-android + net10.0-windows10.0.19041.0) shared-ledger app backed by a single real Supabase project (Postgres + Auth + Storage + Edge Functions + pg_cron), plus two separate web surfaces: a static Cloudflare-Worker site (web/) for invite links, legal pages, and password reset, and a lightweight React SPA (webapp/) for browser-only friends who can't install the Android app or don't have a Windows machine.

It is not just an expense splitter anymore. As of this commit it's a two-vertical friends/family app: shared expenses (N-way split bills, settle-up, recurring templates, receipts, multi-currency) and events & calendar (RSVP, tri-state carpooling, auto-generated birthday events). Both share one GroupDetailPage tab switch, one members/invite system, one push transport, and one localization/theming layer.

The documentation is out of date — by a non-trivial amount

Worth stating plainly rather than softening: CLAUDE.md does not describe roughly the last two days of shipped work. It was last touched at commit de66f3b (2026-09-07). HEAD is 6c3c0c0 (2026-09-09). The diff between those two points is 36 files and ~1,370 inserted lines — and it is not small stuff.

Multi-currency (per-expense currency, a locked group settlement currency, an exchange_rates singleton, two conversion triggers, a daily fetch-exchange-rates Edge Function) and Events & Calendar (RSVP, tri-state carpooling with a seats-offered/needed aggregate, auto-generated birthday events, a second entire push pipeline) — two full features, zero mentions in the one file this whole project's own practice depends on to avoid re-litigating already-fixed bugs.

CLAUDE.md is written as a running engineering journal and is genuinely excellent at what it does — dated, cross-referenced, candid about real bugs found and fixed. That makes the gap more costly, not less: anyone (or any agent) reading it today would conclude the app has no calendar and no currency support. Recommendation: catch it up before the next feature starts, the same way commit 8d992ce already did once before.

A smaller instance of the same pattern: two pre-existing HTML review reports already sit in the repo root — ui-review-report.html and live-ui-walkthrough-report.html. Both date to commit 4eb9221, before the redesign and the UI "juice pass." I spot-checked two of their findings against current XAML: LoginPage.xaml now has the ScrollView + busy-state guards the report said were missing, and the "Join with code / + New group look ugly together" finding is moot — that button pair no longer exists in that shape. Both reports are stale artifacts that will mislead the next reader into re-litigating fixed issues.

02Architecture — this part is genuinely solid

The backend-abstraction rule (Services/I*Repository interfaces, ViewModels never touch Supabase.Client directly) is followed with no exceptions found. Every repository takes the one shared Supabase.Client singleton registered in MauiProgram.cs — exactly one authenticated session object in the whole app.

The MVVM layer is consistent CommunityToolkit.Mvvm end to end, and the standout piece of the whole codebase is that every single async command runs through BaseViewModel.RunSafeAsync (ViewModels/BaseViewModel.cs:24). It turns process-fatal unhandled exceptions (confirmed in the app's own history — a bare AsyncRelayCommand exception fail-fasts WinUI with 0xc000027b) into a plain ErrorMessage string, and transparently retries once on the recurring Supabase clock-skew rejection. A well-reasoned, minimal fix for a real crash class.

The GroupDetailViewModel → GroupExpensesViewModel + GroupEventsViewModel split (done when Events landed) is the right call — the alternative was one ballooning ViewModel covering two unrelated verticals.

Real performance smell: N+1 query patterns, three separate places

A genuine finding, not a style nitpick — and it gets worse as data grows, not better:

  • GroupExpensesViewModel.RefreshActivityAsync (ViewModels/GroupExpensesViewModel.cs:182-227) calls GetSharesAsync(expense.Id) inside a loop over every expense in the group — one round trip per expense, every time the tab loads.
  • GroupEventsViewModel.LoadAsync (:148-151) does the same for attendees — one round trip per event.
  • GroupsViewModel.LoadAsync (:90-105) does it a third time for the groups list — one round trip per group just to build the avatar stack.

None of these are broken — they're correct — but a group with 150 expenses in its history means 150 sequential HTTP round trips just to render "Recent activity." Postgrest supports in filters and embedded/nested selects (expenses?select=*,expense_shares(*)), either of which collapses each of these to one request. This is the single most concrete "will bite you later" finding in the whole review — invisible today because no test group has 150 expenses yet.

Update(model) sends the whole row — a documented, load-bearing footgun

Several places explicitly carry forward fields a fresh model object would otherwise silently reset — AddExpenseViewModel stashing editingCreatedBy/editingCreatedAt/ editingIsSettlement before calling UpdateAsync, ProfileViewModel.SaveProfile mutating the already-loaded member in place. Consistent and well-commented everywhere checked, but entirely convention-enforced — nothing in the type system stops the next new edit flow from silently zeroing CreatedBy/CreatedAt the way it already did once for real (the expenses_created_by_fkey violation documented in the app's own history).

03Backend — schema.sql, 2,413 lines, read in full

A well-run Postgres/RLS schema for a project this size, with self-documentation well above what most side projects bother with — including two genuine 42P17 RLS-recursion postmortems written inline. Specific things worth calling out:

  • The core design decision (members vs. accounts, phantom vs. claimed) is applied consistently — every ledger table points at members, never auth.users.
  • SECURITY DEFINER is used narrowly and every instance is justified in a comment — either a genuine permission gap (the vault schema reads) or RLS-recursion avoidance. None found without a stated reason.
  • The currency conversion trigger fails closed, not open — if exchange_rates has no row yet, it raises rather than silently treating the rate as 1:1. Right call for a ledger, but it means the very first foreign-currency expense on a fresh deploy hard-fails until the daily fetch has run once.
  • Birthday events are a genuinely clever reuse of existing infrastructure — correctly clamping Feb 29 to the target month's real last day instead of crashing on make_date, and deliberately leaving created_by null so nobody gets a delete button the next day's cron would just recreate anyway.
  • Every cron-only / trigger-only function is correctly revoked from anon/ authenticated — checked every one; none reachable via PostgREST's /rpc/ by an ordinary user.

Things that look like live risk, not just design notes

The live Supabase project ref is hardcoded in ten separate cron.schedule(...)/ trigger bodies across schema.sql. Not a secret (correctly reasoned in the file's own comments), but it does mean the file is no longer the portable "run this against a fresh project" script its own header comment still claims to be.

schema.sql itself is a single 2,413-line file hand-edited in place for months — a defensible choice for a single-maintainer project (one canonical fresh-install script instead of an ever-growing migrations folder), but it means the file is a reliable current state, not a reliable history. One soft spot the schema's own comments already flag and this review repeats: the "update events in your groups" policy lets any group member edit any event, including a birthday row — enforced only by the app never exposing that entry point, an honestly-labeled soft protection, not a hard one.

05Setup, tooling, and process gaps

  • No automated tests anywhere — no test project, no xunit/nunit/mstest reference, nothing under webapp/ beyond a linter. Every "confirmed working end to end" note in the app's history is a manual pass, not a regression test. None of the real, subtle bugs already documented (the RLS-recursion pair, the sign-inversion bug, the invite-expiry-defaulting bug) would be caught automatically if they regressed.
  • No CI/CD — .github/ doesn't exist. No automated build gate on push, no lint gate on webapp/. The only verification any change gets is whatever the person (or agent) making it happens to run locally.
  • Secrets handling is correctly done — Config.Local.cs and webapp/.env are both gitignored with committed .example templates; no committed secret found anywhere in the files read.
  • AppUpdateService reads latestVersion from web/version.json but never reads minVersion — the field is deployed, and simply unused.
  • Windows push is a deliberate no-op — every Windows user currently gets zero push for anything. For an app whose entire second vertical leans on push for reminders and carpooling coordination, that's a meaningfully-sized hole on one of only two supported platforms.

06UI / styling system

The design-token discipline (Tokens.xaml, Colors.xaml, Styles.xaml) is real and largely followed, not aspirational. The accent-color feature (8 curated presets, dark-only) is implemented cleanly — colors that should react to the live accent use DynamicResource, everything else StaticResource — and the in-place-dictionary-mutation approach was arrived at only after confirming the more obvious remove-and-readd pattern under-updates real WinUI button chrome. Careful, verified engineering, not a guess that happened to work.

The two old HTML reports (§1) did catch a real, now-fixed high-severity bug and a batch of lower-severity, still-plausible issues — small icon-only tap targets, occasional raw pixel values sitting next to token references. Most of that XAML has since been rewritten by the redesign, so line numbers no longer line up, but the category of issue is still visibly present in newer XAML (e.g. SplitCheckboxStyle's 20×20 tap target is unchanged). A reasonable candidate for a dedicated re-audit now that the redesign has settled, rather than re-litigating finding-by-finding here.

07Concrete strengths worth stating plainly

Easy for a review to read as a list of problems — to be direct about the other side: this is a well-engineered solo/small-team project, above the bar of most side projects at this stage.

Members vs. accounts

The phantom/claimed design is the right foundational call for a shared ledger, applied with real discipline everywhere — no silent violation found.

Bug-fixing rigor

Root causes are chased and explained (two RLS-recursion bugs, a sign-inversion bug, a silent-default bug) — not just patched around.

RunSafeAsync

A small piece of code doing an unusually good job containing a real, previously-fatal crash class app-wide, with no per-ViewModel opt-out to forget.

Shipped and verified

Multi-currency and Events both shipped with real end-to-end verification against the live project, not just a clean compile.

No premature abstraction

No speculative config, no dead feature flags. Grepping the whole app tree for TODO|FIXME|HACK returns zero matches.

Part 2

The council

Everything above is one reviewer's read of the codebase. To pressure-test "what should Axis build next" from more than one angle, the question went to a five-advisor LLM council (adapted from Andrej Karpathy's LLM Council method): five independent advisors, each answering from a deliberately different thinking style, peer-reviewing each other's anonymized answers, then a chairman synthesizing everything into one verdict.

A methodology note worth being upfront about: several advisors and reviewers had tool access and used it — some read CLAUDE.md, schema.sql, EVENTS_PLAN.md, SCOPE.md, and git history directly rather than relying only on the briefing given to them, and the chairman went further, cross-checking claims against Part 1 of this same document. That wasn't instructed, but it made the output substantially stronger — several claims below are verified against the live schema, not just argued.

2.1The question posed to the council

Axis is a .NET MAUI shared-ledger app for a small, invite-only group of friends/family — pre-launch, no public signups yet. Vertical 1: N-way split expenses, settle-up, recurring templates, receipts, full multi-currency, two balance display modes. Vertical 2: group events with RSVP, tri-state carpooling with a seats-offered/needed aggregate, auto-generated birthday events. Shared: Android-only push, aliases, avatars, 8 accent presets, en/es localization, phantom members whose history transfers on claim; plus a narrower React web client for one browser-only friend.

Given everything already built, what should be built next? Features that would make someone go "oh, I want this" — not bug fixes or polish, but genuine product additions that would meaningfully increase value for a small group actively managing shared money and shared plans together. Consider what's plausible for a solo/small-team hobby project to actually build and maintain.

2.2Five advisors, five independent answers

D
Diane
The Contrarian — looks for what's wrong, what will fail

CLAUDE.md itself confirms the gap I'd flag first: it frames events/calendar as a future phase, not-yet-started. Currency shows up once, marked "reserved but unused." Yet two entire verticals are live with zero trace in the one file this project depends on to avoid re-litigating fixed bugs. That's the project's memory silently falling behind its shipped surface.

That's the real constraint on "what's next," not idea supply. This log shows roughly one severe, data-touching bug per shipped feature, caught only after real friends hit it live — backwards balance math, invites silently dead app-wide, two RLS infinite-recursion bugs, a race that told a real member "Group not found." Whatever ships next inherits that tax.

So the filter matters more than the pick: nothing that widens blast radius on money-correctness or adds an unverifiable integration. Do not build bank/Plaid sync — the most tempting "obvious next step" and the one that turns a hobby ledger into a liability. Skip in-app chat too. Anything you add should sit beside the ledger, not inside its math.

M
Marcus
First Principles — rebuilds the question from the ground up

You're asking "what's the next vertical" by extrapolation — expenses, then events, so what's #3? Wrong axis. Money and time-together aren't separate resources — they're the same occasion viewed from two angles. A trip is an event and a pile of expenses. Right now those are parallel data models with no edge between them: an event doesn't know its expenses, and the RSVP list isn't the list you split the bill against three weeks later.

So: don't build vertical 3. Build the join. Let an event optionally own a scoped ledger — expenses attached to it, default split pulled from "going" RSVPs, a running total on the event page, settle-up prompted once the date passes. This reuses your split engine, your settle-up model, your RSVP data, your push triggers. It's a foreign key and some UI, not a subsystem.

And it kills the exact annoying moment this group hits: reconciling "who was on this trip" against "who paid for what" as two separate memories instead of one screen.

A
Alexandra
The Expansionist — looks for the upside everyone else missed

The vision doc already says it: "one unified channel per group," not a separate splitting app and a separate calendar app. Nobody's built the fusion yet. The single biggest swing: Trip Mode — let an Event become a container for expenses. RSVP to the cabin weekend, every expense tagged to it rolls into a running trip total, split only among whoever's actually going, visible live instead of reconstructed afterward from a date range.

Second, nearly free: a Recap. After a trip, month, or year, auto-generate a shareable summary — total spent, cost per person per day, who fronted the most, photos if the receipts pipeline gets reused for an album. Zero new infrastructure, exactly the kind of thing that gets screenshotted into the group chat unprompted.

Third, criminally underused: birthdays already auto-generate as events — wire group gift pooling off one, "chip in for Dave's gift," kept off Dave's own feed. Stop treating these as two apps that share a login.

S
Sam
The Outsider — zero context, reacts to what's in front of them

Zero context, so I'm reacting to the two-vertical description itself — the split is the tell. "Vertical 1/2" is an engineering frame, not how a friend group experiences a trip. Nobody planning "Lake Trip" opens the events product, then separately the money product. The obvious next build: let an expense optionally attach to an event, so opening "Lake Trip" shows who's coming, who's driving, and a running per-person cost in one place. Currency conversion is already solved, so a live "$340 spent, ~$85/head" total is nearly free.

Second, just as obvious from outside: you already solved photo upload/resize/storage for receipts — point that at events and give each trip a shared album. "Pictures from the trip" is the most viscerally wanted thing by an actual friend group, more than any ledger feature.

Third: confirm carpool/RSVP changes actually push a notification. Carpooling only works socially if the person offering a seat finds out the moment someone claims it.

R
Rosa
The Executor — can this be done, what's Monday morning

Two features ship this week because you already built 90% of their plumbing.

1. Recurring-expense due reminders. materialize_recurring_expenses already runs daily; send-push is already proven end to end. Write upcoming_recurring_reminders() mirroring the existing shape, call it right after materialization. No new table, no new screen, no new push plumbing. The single most "oh I want this" feature for the actual use case here: rent day.

2. Google Calendar sync, as a read-only ICS feed, not OAuth. You already have battle scars from Google OAuth on Windows. One Edge Function emitting a static .ics feed; every calendar app subscribes to a URL natively — zero OAuth. Half a day.

Skip anything needing a new UI paradigm — polls, chat, budgets — until these two are deployed.

2.3Peer review — what the advisors caught in each other

All five responses were anonymized and cross-reviewed. The pattern was unusually consistent:

  • Strongest responseSplit between Marcus ("build the join," 3 of 5 reviewers) and Alexandra (Trip Mode + Recap + gift-pooling, 2 of 5) — never a real contest, since both argue the same core idea. One reviewer verified the load-bearing claim directly against schema.sql: expenses genuinely has no event_id column.
  • Weakest response, unanimouslyDiane. All five reviewers independently flagged the same thing — her documentation-drift catch is real and her risk framing is sound, but she proposed zero features against a question that explicitly asked for features.
  • Missed by all five — the web appThree reviewers independently flagged it: webapp/'s router has zero Events routes, so if event-expense linking ships native-only, the one person the web client exists for can't use the feature the rest of the group starts relying on.
  • Missed by all five — the real fix nobody namedOne reviewer: updating CLAUDE.md/SCOPE.md to match what's shipped may itself be the highest-leverage "build" available, given this project's history of bugs surfacing when docs lag code — and no advisor said so outright.
  • Missed by all five — offline resilienceEvery flagship pitch (a live running trip total) targets exactly the low-connectivity moments — cabins, hikes, travel abroad — where a live round trip can't be assumed.
  • Missed by all five — notification fatigueMultiple advisors independently propose more auto-push triggers on a week-old pipeline with no mute/preference mechanism anywhere yet.
  • Missed by all five — the ironyThe consensus pick is exactly the failure shape that already bit this project twice: both real production RLS bugs to date came from two tables' policies referencing each other. Wiring expenses to events is a new cross-table relationship, in a codebase with zero tests to catch a repeat.

One additional finding, verified after the chairman synthesis was already under way (so the verdict below doesn't reflect it, but it's real): a fifth review, cross-checking schema.sql's actual trigger list, found that events has exactly three triggers — insert / update / before-delete — and none are on event_attendees. In plain terms: today, changing an RSVP or a carpool offer/need fires no push notification at all — only creating, editing, or cancelling the event itself does. Sam's "confirm carpool/RSVP changes actually push" instinct was, per this check, a real gap, not a redundant ask.

The same review flagged a structural question nobody else raised: a phantom member cannot RSVP at all, since every event_attendees write policy requires m.account_id = auth.uid(). For an app whose founding principle is that phantom members participate exactly like anyone else, RSVP is quietly the first feature where that principle doesn't extend — worth a deliberate decision, not an accidental gap.

2.4The chairman's verdict

Council verdict

Build the join, not a third vertical — but fix the map first

Where the council agrees

The event-expense fusion is the standout idea, reached three independent ways. Marcus (first-principles), Alexandra (expansionist), and Sam (outsider) all landed on the same mechanism — an event optionally owns a scoped set of expenses, default split from "going" RSVPs, a running total on the event page, settle-up prompted once the date passes. Four of five peer reviewers ranked this strongest, and the chairman confirmed the load-bearing claim directly: expenses has no event_id anywhere in schema.sql.

It's structurally cheap, not just appealing. Both tables already gate access through the identical is_group_member(group_id) RLS pattern, so a nullable expenses.event_id needs no new policy and no cross-table recursion risk — the same "scope by group, not by parent row" trick the schema already uses for receipt paths.

Nobody wants a third vertical. No advisor proposed a genuinely new domain — budgets, chores, shopping lists, polls. The council converges hard on connect what's built over add what isn't.

Diane's documentation-drift finding is real, and every reviewer said so — confirmed precisely: CLAUDE.md was last edited two days before HEAD, a gap of 36 files / two entire features. Part 1 of this document, written independently the same morning, reached the identical conclusion by a completely different route.

Where the council clashes

Diane's guardrails vs. everyone else's appetite to ship. Every reviewer penalized Diane for answering with prohibitions, not features. Fair against the letter of the brief — but her evidence (one severe bug per shipped feature, zero tests) still holds, and both real recursion bugs to date came from cross-table policy references — the same risk class as this pick. Ship it, but the way the schema already knows how to dodge this exact failure mode.

Rosa's "ship this week" vs. the fusion feature. Rosa frames her two picks as substitutes — "skip anything needing a new UI paradigm until these two are deployed." A real disagreement: cheapest-win-this-week vs. highest-leverage-single-feature. Both reasonable; they can't both be first.

Rosa's ICS pitch is good, but isn't "next per the roadmap" as claimed — the project's own scope doc already plans a heavier OAuth-based Google Calendar sync, deliberately deferred until Events shipped. Rosa's read-only ICS feed is a smarter, cheaper substitute for that — not a continuation of the existing plan.

Blind spots the council caught
  • The web-only friend loses the exact feature the group would use together — webapp/src/App.tsx has zero Events routes, not partial, not stubbed.
  • Notification fatigue is a debt the project already wrote down — a deferred "per-group notification muting" item exists in the project's own plans, and there's still no mute mechanism anywhere.
  • The mixed-currency concern raised in peer review is already solved — groups.currency is locked at creation and every expense snapshots its converted amount, so an event total is a plain sum(), no new design needed.
  • Sam's "confirm carpool/RSVP pushes work" is more right than peer review gave credit for — see the supplementary finding above: event_attendees genuinely has no push trigger today.
  • Offline resilience, unaddressed by all five — every repository call is a live round trip with no local cache; Trip Mode's real usage moments (cabins, hikes, abroad) are exactly where connectivity is worst.
  • Windows gets zero push, and every reminder/carpool nudge the council proposes is an Android-only win.
The recommendation

Build the event-expense link — Marcus's scoping, exactly as written: nullable expenses.event_id, default split from "going" RSVPs, a running total on the event page, settle-up prompted once the date passes. The one idea on the table that is genuinely a feature, that makes both verticals better at once, and that the codebase can absorb safely.

Ship it with three guardrails the evidence makes non-optional:

  1. Decide the web-client question before shipping — scope a minimal linked view into webapp/, or ship an explicit "not on web yet" indicator. No silent widening of an already-documented gap.
  2. No fourth push trigger type before the mute control the project already designed exists. Build the mute mechanism now, not after the next trigger makes it more urgent.
  3. Additive-only migration — nullable FK, no new policy touching events' own RLS, manual re-verification of the two known recursion-prone paths afterward. Given zero test coverage, this is the one place that needs a specific, not general, brake.

Do Rosa's two picks next — real, cheap, and on different schema surface, so there's no reason to choose between them and the fusion feature. Just don't let them substitute for it.

The one thing to do first

Catch CLAUDE.md and SCOPE.md up to what's actually shipped — before writing the event_id migration, as its first step, not a detour from it. Part 1 of this document already did the investigation; this is transcription, a few hours, not a project. Whoever builds the join next — human or agent — will read CLAUDE.md first, per this project's own stated practice, and right now that file doesn't know events exists. Building a cross-table schema change on docs that don't know the other table exists, with no test suite to catch the mistake, is the one sequencing error that would compound every risk this council surfaced. Fix the map, then build the join.

Part 3

Closing synthesis

Two independent processes — a cold read of the codebase (Part 1) and a five-advisor council debating product direction from adversarial angles (Part 2) — converged on the same starting point without either one steering the other: the documentation is the bottleneck, not the idea supply. Part 1 flagged CLAUDE.md's two-day, 36-file, two-feature gap as finding #1 before any council question was asked. The council, reasoning purely about "what to build next," independently rediscovered the same gap through Diane's contrarian pass, had it confirmed by every peer reviewer, and the chairman named fixing it "the one thing to do first" — ahead of the feature idea the rest of the council spent its energy on. When two differently-motivated passes over the same project land on the same top priority without coordinating, that's about as strong a signal as this kind of review can produce.

The product answer underneath is good for a specific, checkable reason rather than because it sounded appealing: event-expense linking is the only idea the council proposed that is verifiably cheap in this exact codebase — a nullable foreign key riding RLS machinery that already exists, not a new subsystem — while also being the only idea that addresses a friction real users would recognize immediately. It also sits directly on top of this review's own §2 performance finding: the N+1 query patterns will get real exercise the moment expenses start rendering inline on event pages, so fixing those loops stops being hygiene and becomes a prerequisite.

Put together, the punch list in §8 and the council's verdict in §2.4 point at the same short sequence: update the docs, collapse the N+1 loops, then build the join — in that order, because each step makes the next one safer in a codebase that currently has no automated safety net of its own.
